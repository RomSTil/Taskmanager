# ТЗ: Автономная команда Codex в TaskManager

## 1. Цель

Превратить TaskManager из списка задач в операционный центр автономной команды
Codex. Владелец ставит бизнес-цель одной кнопкой, агенты сами выполняют
исследование, работу в браузере, разработку, проверку и подготовку результата.
Владелец не пишет промежуточные ТЗ и не управляет исполнителями. Его роль -
оценить готовый результат и принять решение только там, где нужны вкус,
деньги, публикация, внешняя коммуникация или необратимое действие.

Первая среда исполнения - персональный компьютер владельца под Windows. Это
позволяет Codex пользоваться отдельным браузерным профилем и сайтами без API.
TaskManager и MAX доступны из любого места и выступают очередью работ и
панелью принятия решений.

## 2. Границы первого релиза

В первый релиз входят:

- постановка поручения из веб-интерфейса TaskManager и MAX;
- очередь запусков и локальный `Taskman Agent Runner` на Windows;
- оркестрация ролей: координатор, исследователь/разработчик, тестировщик,
  визуальный ревьюер;
- Codex как среда исполнения, TaskManager MCP как доступ к проектам, задачам
  и заметкам;
- карточки прогресса и согласований в веб-интерфейсе и MAX;
- финальная оценка владельца, цикл доработки и явное принятие результата;
- журналы действий, отмена запусков, лимиты параллелизма и безопасные политики.

Не входят в первый релиз:

- самостоятельная оплата, заказ товаров, подписание документов или отправка
  юридически значимых сообщений;
- круглосуточный запуск неограниченного числа агентов;
- передача браузерных паролей, cookies и ключей с ПК на сервер;
- автоматический production-deploy без отдельного подтверждения владельца.

## 3. Продуктовые принципы

1. Агент выполняет цель, а не создаёт документы ради документов. Внутренние
   планы, таблицы и заметки создаются только как рабочие артефакты.
2. Обычная задача должна попадать в работу за одно действие: `Поручить Codex`.
3. Владелец видит только важные события: старт, блокировка, запрос решения,
   готовый результат и ошибка.
4. Агент сам выбирает следующий шаг в рамках политики, а не спрашивает
   разрешение на каждую мелочь.
5. Любая внешняя, финансовая, публикационная или необратимая операция требует
   отдельного решения владельца.
6. Результат разработки не считается завершённым без оценки владельца.
7. Все роли работают с одной задачей через TaskManager MCP; их история и
   артефакты доступны в карточке запуска.

## 4. Роли агентов

### 4.1. Координатор

Получает цель, читает задачу и связанный контекст через MCP, выбирает профиль
работы, назначает исполнителей, контролирует критерии готовности и собирает
финальный результат. Координатор не должен сам выполнять тяжёлую работу, если
её можно передать специализированной роли.

### 4.2. Исследователь / закупщик

Работает в браузере: ищет поставщиков, цены, характеристики, наличие,
сертификаты, контакты и варианты. Сам создаёт структурированный итог в
TaskManager. Может подготовить письма и заявки, но не отправляет их без
согласования.

### 4.3. Программист

Работает только в отдельной Git worktree/ветке. Изучает репозиторий, реализует
изменение, запускает локальные тесты и создаёт preview. Не пушит в `main`, не
деплоит и не меняет production без отдельной команды процесса.

### 4.4. Тестировщик

Получает результат программиста и исходную цель. Выполняет автоматические
тесты, проверяет ключевые пользовательские сценарии и мобильную версию.
Возвращает только найденные дефекты с воспроизводимыми шагами либо вердикт
`готово к оценке владельца`.

### 4.5. Визуальный ревьюер

Проверяет сайт и интерфейсы как строгий арт-директор: шаблонность,
"нейрослоп", иерархию, текст, контраст, адаптивность, соответствие бренду и
цели страницы. Он не подменяет вкус владельца, а фиксирует внутренние
замечания до показа результата.

### 4.6. Деплой-агент

В первом релизе не запускается автоматически. Его задача доступна только после
явного действия владельца `Принять и опубликовать`.

## 5. Сценарии работы

### 5.1. Исследовательская задача

Пример: `Поиск ведер`.

1. Владелец нажимает `Поручить Codex`.
2. Координатор сам формирует критерии: ёмкость, пищевой материал, крышка,
   ручка, цена, MOQ, доставка, документы, срок поставки.
3. Исследователь работает в браузере и собирает предложения.
4. Тестировщик проверяет, что достигнуты критерии и ссылки не выдуманы.
5. Владелец получает не отчёт ради отчёта, а рекомендованный вариант и кнопки:
   `Принять`, `Написать поставщикам`, `Переделать поиск`.
6. При выборе `Написать поставщикам` агент показывает подготовленные обращения;
   отправка выполняется только после явного подтверждения.

### 5.2. Разработка сайта

Пример: обновить карточки продукции на GarlicCompany и GarlicTula.

1. Координатор собирает контекст товара и сам создаёт исполнимые подзадачи.
2. Программист меняет код в worktree и собирает preview.
3. Тестировщик и визуальный ревьюер проверяют preview.
4. Владелец получает ссылку на preview и три действия: `Принять`,
   `Написать замечание`, `Переделать`.
5. Замечание владельца передаётся координатору как приоритетный факт. Он сам
   превращает его в задачи программисту/дизайнеру.
6. После `Принять` владелец отдельно видит `Опубликовать`. Только эта команда
   создаёт deployment job.

### 5.3. Цикл замечаний владельца

Владелец может написать свободный текст, например: "слишком шаблонно, первый
экран выглядит нейрослопно, переделать композицию". Система не просит его
оформлять ТЗ. Координатор обязан:

1. подтвердить, какие изменения он понял;
2. создать подзадачи для нужных ролей;
3. отправить результат на новую оценку;
4. не помечать запуск принятым до действия владельца.

## 6. Состояния

Статус обычной задачи (`inbox`, `todo`, `in_progress`, `blocked`, `done`) не
изменяется и сохраняет обратную совместимость. Новый жизненный цикл хранится в
отдельном `agent_run`:

```text
queued
  -> planning
  -> running
  -> internal_review
  -> waiting_owner_review
  -> accepted
  -> completed

running/internal_review -> waiting_approval -> running
waiting_owner_review -> revision -> running
любой активный статус -> cancelled | failed | blocked
```

`waiting_approval` используется для внешнего, финансового, публикационного или
необратимого действия. `waiting_owner_review` означает: работа выполнена и
требует именно субъективной оценки владельца.

## 7. Модель данных

### 7.1. `agent_runs`

| Поле | Назначение |
| --- | --- |
| `id` | UUID запуска |
| `task_id` | исходная задача TaskManager |
| `parent_run_id` | родительский запуск для делегирования |
| `goal` | цель владельца без технических деталей |
| `status` | состояние из раздела 6 |
| `mode` | `auto`, `fast`, `analysis`, `maximum` |
| `selected_model` | фактически выбранная доступная модель Codex |
| `selected_effort` | уровень reasoning |
| `role` | текущая ответственная роль |
| `runner_id` | Windows-устройство, исполняющее запуск |
| `approval_policy_id` | применённая политика действий |
| `result_note_id` | заметка с результатом, если нужна |
| `preview_url` | ссылка на preview для оценки |
| `error_code`, `error_message` | нормализованная ошибка без секретов |
| `created_at`, `started_at`, `finished_at` | аудит и SLA |

### 7.2. `agent_run_steps`

Отдельная запись для каждого назначения роли: входной контекст, исполнитель,
статус, ссылка на артефакт, число попыток, время начала/завершения.

### 7.3. `agent_events`

Неизменяемый журнал: запуск, делегирование, tool call summary, созданная заметка,
запрос согласования, решение владельца, ошибка, отмена. Секреты, полный текст
cookies, пароли и OAuth-токены в него не попадают.

### 7.4. `agent_approvals`

Содержит тип действия, краткое объяснение последствий, сумму/домен/preview при
наличии, состояние (`pending`, `approved`, `rejected`, `expired`), владельца и
время решения. Одно подтверждение привязано к одному идемпотентному действию.

### 7.5. `agent_runners`

Реестр локальных исполнителей: имя ПК, публичный ключ/одноразовый device token,
версия runner, время последнего heartbeat, доступные возможности (browser,
git, docker, Codex), лимит параллельности и состояние.

## 8. Backend и API

Новый модуль: `app.modules.agent_operations`. Он зависит от `auth`, `work`,
`notes`, `events`, `notifications` и `max_bot`.

HTTP-запросы не выполняют работу сами. Они создают транзакционные записи и
события; исполнение производится worker-ом или локальным runner.

Минимальные endpoints:

```text
POST   /api/v1/agent-runs
GET    /api/v1/agent-runs
GET    /api/v1/agent-runs/{id}
POST   /api/v1/agent-runs/{id}/cancel
POST   /api/v1/agent-runs/{id}/feedback
POST   /api/v1/agent-runs/{id}/approvals/{approval_id}/decision
POST   /api/v1/agent-runs/{id}/accept

POST   /api/v1/agent-runners/register
POST   /api/v1/agent-runners/{id}/heartbeat
POST   /api/v1/agent-runners/{id}/claim
POST   /api/v1/agent-runs/{id}/events
POST   /api/v1/agent-runs/{id}/complete
```

`claim` возвращает не произвольный shell prompt, а подписанное поручение с
ограниченной политикой, идентификатором запуска и разрешёнными ролями.
Захват задания должен быть атомарным (`FOR UPDATE SKIP LOCKED` либо
эквивалентный безопасный механизм) и иметь lease/heartbeat для восстановления
после выключения ПК.

## 9. Taskman Agent Runner на Windows

Runner - отдельное локальное приложение/служба. Он работает от имени владельца
и только исходящими HTTPS-запросами подключается к TaskManager. Сервер никогда
не подключается напрямую к ПК.

Обязанности runner:

1. регистрировать устройство и регулярно отправлять heartbeat;
2. получать одно поручение в рамках заданного лимита;
3. запускать изолированную сессию Codex с целью, ролью, модельным профилем и
   TaskManager MCP;
4. передавать в сервер структурированные события и краткий прогресс;
5. останавливать процесс при отмене/истечении лимита;
6. очищать временные worktree и browser context после завершения;
7. не выгружать пароли, cookies и локальные файлы на сервер.

Для первого релиза: один доверенный runner, один активный запуск, опрос очереди
каждые 15-30 секунд. Дальше - WebSocket/long polling и несколько устройств.

Runner использует уже настроенный `taskman-mcp`. Для production-режима он
получает отдельный MCP/API-token со scopes только на проекты, задачи и заметки.
Токен хранится в Windows Credential Manager, не в `.env` и не в базе сервера.

## 10. Интеграция Codex и MCP

Codex получает роль через системную инструкцию запуска и MCP-инструменты
TaskManager: чтение проектов/задач/заметок, создание подзадач, комментариев,
заметок и обновление статусов.

Правило для каждой роли:

```text
Работай до достижимого бизнес-результата.
Не создавай объясняющие документы, если они не нужны для действия или решения.
Фиксируй в TaskManager только проверяемые факты, ссылки, принятые решения,
результаты и блокировки.
Не выполняй действие, требующее approval, без активной записи approval.
```

Модельный профиль `auto` выбирается серверной политикой из доступных в Codex
моделей, а не произвольным названием модели из пользовательского ввода:

| Профиль | Назначение | Требование |
| --- | --- | --- |
| `fast` | короткие выборки, классификация, статусы | низкий reasoning |
| `analysis` | исследование, сравнение, обычная разработка | средний reasoning |
| `maximum` | сложная архитектура, крупные изменения, глубокий аудит | высокий reasoning и явный лимит времени |

Если выбранная модель/effort недоступны по подписке, runner берёт заранее
настроенный fallback и пишет это в `agent_events`.

## 11. Веб-интерфейс TaskManager

### 11.1. Карточка задачи

Добавить кнопку `Поручить Codex`. Модальное окно содержит только:

- цель (по умолчанию заголовок и описание задачи);
- режим: `Авто`, `Быстро`, `Анализ`, `Максимум`;
- разрешённые действия: `только исследование`, `работа в браузере`,
  `изменение кода в preview`;
- кнопку запуска.

Не показывать владельцу технический prompt, внутреннее ТЗ или перечень
субагентов до тех пор, пока он не откроет подробности намеренно.

### 11.2. Экран «Работа агентов»

Новый раздел sidebar. Карточка запуска показывает цель, статус, текущую роль,
краткий человеческий прогресс, preview, результат и только нужные действия.

```text
Идёт работа                 -- кнопка «Остановить»
Нужно твоё решение          -- понятная причина и 2-3 действия
На твоей оценке             -- preview, «Принять», «Замечание», «Переделать»
Готово                      -- краткий итог и ссылки на результат
```

Технический event log доступен по раскрытию и используется для отладки, но не
является основным интерфейсом.

### 11.3. Оценка владельца

В форме оценки есть свободный текст и быстрые ярлыки:

- `Слишком шаблонно`;
- `Не соответствует бренду`;
- `Нужна другая логика`;
- `Есть баг`;
- `Принято`.

Ярлык добавляется в feedback вместе с текстом. Координатор обязан повторить
смысл замечания кратко, а затем запустить доработку без требования формального
ТЗ от владельца.

## 12. MAX-бот

Расширить существующий MAX-модуль новым типом интеграции `operations`, не
ломая текущие `direct` и `market` сценарии.

Меню:

```text
🤖 Поручить работу
📌 Мои активные работы
⏸ Нужны решения
✅ Готово на оценку
```

MAX-бот принимает свободный текст только от разрешённых пользователей. Он
создаёт draft поручения и предлагает выбрать проект/режим. После запуска он не
спамит событиями: максимум сообщения о старте, блокировке, запросе approval и
готовом результате. Каждая кнопка имеет короткий подписанный callback id,
идемпотентна и проходит через существующий durable MAX outbox.

Пример карточки:

```text
🧩 Готова страница товара
Проверка: тесты пройдены, найдено 1 визуальное замечание.
Preview: <ссылка>

[✅ Принять] [✏️ Написать замечание] [↩️ Переделать]
```

## 13. Политики безопасности и согласований

| Класс действия | По умолчанию | Пример |
| --- | --- | --- |
| Чтение и исследование | разрешено | поиск поставщиков, чтение сайта |
| Локальные черновики | разрешено | worktree, preview, заметка |
| Изменение кода вне `main` | разрешено | ветка и тестовая среда |
| Внешнее сообщение | approval | письмо поставщику, сообщение клиенту |
| Публикация | approval | deploy, публикация карточки |
| Деньги | approval с суммой | заказ образцов, оплата рекламы |
| Удаление/необратимое изменение | approval | удаление данных, отключение кампании |

Пользователь может задать лимиты: максимальное число параллельных запусков,
максимальная длительность, разрешённые домены браузера, максимальная сумма
одного approval. Runner использует отдельный браузерный профиль
`Taskman Agent`; основной профиль владельца не используется.

## 14. Надёжность и наблюдаемость

- Все задания, callbacks, approvals и уведомления идемпотентны.
- У задания есть lease; после потери heartbeat оно возвращается в очередь либо
  переходит в `blocked` с понятной причиной.
- Автоматические повторы допустимы только для сетевых ошибок и не для внешнего
  действия с побочным эффектом.
- Любая ошибка видна владельцу без технического стека: что не сделано, почему,
  что можно нажать дальше.
- Логи содержат correlation id запуска, но не содержат секретов, паролей и
  содержимого закрытых сессий.
- Для кода обязательны worktree, тесты и возможность сравнить diff до принятия.
- Нужны health endpoint runner и dashboard: online/offline, активный запуск,
  последняя ошибка, версия runner.

## 15. Критерии приёмки

### MVP: исследование

1. Владелец запускает `Поиск ведер` из TaskManager или MAX одной кнопкой.
2. Локальный runner принимает работу и отображается как online.
3. Codex через MCP читает задачу, работает в браузере и создаёт итоговую заметку.
4. Итог содержит проверяемые ссылки, параметры и рекомендацию.
5. Владелец получает MAX-карточку `Готово на оценку`.
6. По feedback агенты выполняют доработку без нового ручного ТЗ.
7. Отправка сообщения поставщику невозможна без approval.

### MVP: разработка

1. Агент создаёт отдельную worktree и не меняет `main`.
2. Программист, тестировщик и визуальный ревьюер имеют отдельные шаги запуска.
3. Владелец получает preview и может принять либо вернуть с текстовым отзывом.
4. Production deploy невозможен до `Принять и опубликовать`.
5. После публикации TaskManager хранит ссылку на run, commit/diff, тесты и
   решение владельца.

## 16. Порядок реализации

### Этап 1. Фундамент

Модуль `agent_operations`, миграции, `agent_runs`, `agent_events`, approvals,
REST API, экран запусков, audit tests. Использовать существующий паттерн jobs и
outbox, не создавать второй несовместимый worker.

### Этап 2. Windows Runner и один исследователь

Регистрация устройства, polling/lease, запуск Codex с TaskManager MCP,
исследовательская роль, прогресс, отмена, MAX-уведомления. Проверить на
`WORK5-1 Поиск ведер`.

### Этап 3. Оценка владельца

Preview, feedback, цикл доработки, визуальный ревьюер, политика approval.

### Этап 4. Разработка

Worktree, программист, тестировщик, preview, review/deploy gate. Проверить на
задаче обновления сайтов.

### Этап 5. Масштабирование

Несколько runner, расписания, специализированные профили для закупок,
маркетинга и разработки, лимиты и аналитика потребления Codex.

## 17. Решение по первой демонстрации

Первым production-пилотом является `WORK5-1 Поиск ведер`. Он безопасен,
измерим и даст реальную пользу: агент должен выдать поставщиков пищевой тары
на 1, 5 и 10 кг с рекомендацией, а владелец оценивает качество результата.
После успешного пилота вторая задача - `WORK3-5 Создать компанию для продукции`,
где проверяется полный цикл programmer -> QA -> owner review -> deploy gate.
