# Аудит безопасности Taskman

Дата проверки: 23 июля 2026 года.

## Область проверки

Проверены FastAPI API, SQLAlchemy-модели и миграции, файловое хранилище заметок,
Telegram worker/webhook, MCP bridge, актуальный React/Tauri-клиент, Docker/Caddy и CI.
Запускались backend-тесты, Ruff, `npm audit` для обоих клиентов и `pip-audit`.

Это ревью исходного кода и зависимостей, а не внешний pentest работающего production-стенда.

## Что учесть при развёртывании

- Старые access JWT не содержат новые обязательные claims и потребуют refresh или повторный вход.
- Production теперь не запускается без явных JWT/setup/encryption secrets, HTTPS public URL и
  списка trusted hosts. Это намеренный fail-closed.
- Удалённый backend по HTTP больше не принимается desktop/MCP-клиентами; HTTP оставлен только для
  `localhost`, `127.0.0.1` и `::1`.
- Миграция БД для этих изменений не требуется. Новый `Cargo.lock` следует хранить в Git.

## Исправлено

### Критический риск

- API-токен с любым минимальным scope мог вызывать `/auth/tokens` и выпускать новый токен
  с правами записи. Тем же способом он мог управлять Telegram-интеграциями. Управление
  токенами и интеграциями теперь требует owner-only scopes, которые нельзя выдать API-токену.

### Высокий риск

- Production принимал development JWT secret, необязательный setup token и произвольный
  encryption key. Приложение теперь прекращает запуск при небезопасной production-конфигурации.
- Refresh-токен можно было одновременно переиспользовать в нескольких запросах. Ротация теперь
  выполняется одним условным SQL UPDATE и является атомарной.
- `cryptography 45.0.7` попадал под известные security advisories, а прежнее ограничение `<46`
  запрещало установить исправление. Диапазон поднят до `48.0.1+`, CI запускает `pip-audit`.
- У актуального Tauri-клиента CSP был отключён. Добавлена CSP, удалён неиспользуемый opener plugin
  и его разрешение.
- Desktop/MCP-клиенты могли отправить bearer-токен на удалённый HTTP-сервер. Незашифрованный HTTP
  теперь разрешён только для loopback-адресов.

### Средний риск

- Добавлено ограничение частоты неудачных входов и одинаковая дорогостоящая проверка пароля для
  существующего и несуществующего пользователя.
- Динамический текст Telegram экранируется перед использованием `parse_mode=HTML`; секреты бота
  больше не попадают в диагностические строки сетевых ошибок.
- Сравнение webhook secret выполняется в constant time, некорректный `update_id` возвращает 422.
- Клиенты заметок больше не могут писать в служебные `.taskman` и `_assets`; идентификатор заметки
  проверяется как UUID, пути и имена вложений дополнительно нормализуются.
- Task hierarchy проверяется на циклы и принадлежность одному проекту. Изменения проектов, задач и
  checklist блокируют строку на время optimistic-lock проверки в PostgreSQL.
- Добавлены Trusted Host, защитные HTTP-заголовки, ограничения длины поисковых запросов, ID,
  путей, тегов и общего размера request body. Ошибки уникальности теперь возвращают
  контролируемые 409 вместо 500.
- CI переключён с устаревшего `desktop/` на клиент из `frontend/task manager/`.

## Оставшиеся риски

### P1 — до публичного многопользовательского запуска

- Заметки хранятся одновременно в БД и файловом vault. Транзакция SQL и переименование файла не
  являются общей атомарной транзакцией: авария между операциями может оставить orphan-файл или
  рассинхронизировать индекс. Нужен журнал файловых операций с recovery/reconciliation job либо
  единое object storage/DB-хранилище с outbox.
- Refresh- и access-токены web/Tauri-клиента сохраняются в `localStorage`. CSP уменьшает вероятность
  XSS, но при XSS токены всё равно доступны JavaScript. Для Tauri refresh-токен следует перенести
  в OS credential store/Stronghold, access-токен держать только в памяти.
- Модель данных пока является single-workspace: проекты, задачи и заметки не имеют `workspace_id`
  и membership ACL. До добавления нескольких пользователей нужны Workspace, Membership, роли и
  обязательные tenant-фильтры во всех репозиториях.

### P2 — эксплуатационная устойчивость

- Login limiter хранится в памяти одного процесса. При нескольких API replicas нужен общий backend
  (например, Redis) и rate limit на reverse proxy.
- Backend отклоняет слишком большой declared `Content-Length`, но production proxy всё равно
  должен ограничивать chunked request body и время чтения, не полагаясь только на приложение.
- Вложения проверяются по размеру и безопасному пути, но не по реальному MIME/magic bytes и не
  сканируются антивирусом. Нельзя раздавать их как active content без отдельного download endpoint
  с `Content-Disposition: attachment` и `nosniff`.
- `operation_log`, Telegram update log, revisions и неуспешный outbox растут без retention policy.
  Нужны фоновые cleanup jobs, метрики и dead-letter политика.
- Резервные копии не шифруются самим приложением. Шифрование и контроль доступа должны быть
  обеспечены на уровне диска/object storage, а восстановление — регулярно тестироваться.

## Результат сканирования зависимостей

- `npm audit`: 0 известных уязвимостей в актуальном и legacy desktop lock-файлах.
- До исправления `pip-audit`: проблемы в `cryptography 45.0.7`, `pip 25.0.1`,
  `pytest 8.4.2`.
- После обновления: 0 известных уязвимостей; локальные пакеты `taskman-api` и `taskman-mcp`
  ожидаемо пропущены, так как не опубликованы в PyPI.
